Key Design Decisions

  • No WordPress, no external SaaS — entire system runs on Cloudflare infrastructure
  • Cloudflare Pages Functions — serverless Workers auto-deployed from functions/ directory
  • D1 (SQLite) for persistence — zero-config, edge-local, SQL-based
  • Static fallback — all APIs work without D1 binding using inline service data
  • Structured JSON responses — every API returns data ready for GTM/GA4 tracking

TablePurposePhase

Bookings Table (key columns)

CREATE TABLE bookings (
  id                  TEXT PRIMARY KEY,        -- bc_book_xxx
  transaction_id      TEXT NOT NULL UNIQUE,    -- bc_txn_xxx (for GA4 purchase dedup)
  service_id          TEXT NOT NULL,
  booking_date        TEXT NOT NULL,           -- YYYY-MM-DD
  booking_time        TEXT NOT NULL,           -- HH:MM
  patient_name        TEXT NOT NULL,
  patient_phone       TEXT NOT NULL,
  price_eur           REAL NOT NULL,
  gclid               TEXT DEFAULT '',         -- Google Click ID (closed-loop)
  status              TEXT CHECK(status IN ('confirmed','completed','cancelled','no_show')),
  physician_id        TEXT DEFAULT NULL,       -- Phase 2
  created_at          TEXT DEFAULT (datetime('now'))
);

6. GTM/GA4 Integration Strategy

Conversion Tracking Chain

  1. bc_form_submit — fires on "Conferma" click (intent only, NOT a conversion)
  2. bc_booking_confirmed — fires on API 201 success response
  3. generate_lead — paired with bc_lead_generated (NOT on form submit)
  4. purchase — paired with bc_booking_confirmed (deduped by transaction_id)

DataLayer Push (on confirmation)

// Fired by CGE (BCG.fireBookingConfirmed) or fallback direct push
dataLayer.push({
  event: 'bc_booking_confirmed',
  bc_lead_id: 'bc_book_mlqivxur_5579b80c',
  bc_specialty: 'laboratorio',

  bc_physician_name: 'none',

8. Scalability Model (Future Phases)

Phase 2: Physician Agendas

  • Add physicians, physician_services, physician_schedule tables
  • New endpoint: GET /api/booking/physicians?specialty=cardiologia
  • Step 0 in booking wizard: "Choose physician (optional)"
  • Each physician has independent schedule_rules and capacity
  • bookings.physician_id column already exists (NULL for lab-only)

Phase 3: Multi-Department

  • All tables use department column — already partitioned
  • New routes: /cardiologia/prenota/, /ginecologia/prenota/
  • Same API, different department filter parameter
  • Shared booking engine JS with department config injection

Phase 4: Admin Dashboard

  • Protected /admin/ route with Cloudflare Access (Zero Trust)
  • D1 queries for booking management (cancel, reschedule)
  • Schedule override management (holidays, closures)
  • Analytics dashboard with booking conversion data
